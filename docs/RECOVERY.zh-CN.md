# 清理与故障恢复

停止请求、清理指令发送、后端确认（如有）和真实定位恢复是不同证据，不可互相替代。

## Android

本版先停止调度，再尝试移除本项目写前日志中的 framework 测试源，全部返回成功后才显示清理确认。Google FLP 尚未接入，不能宣称已调用其退出接口。公开 API 不提供完备的并发工具归属证明，恢复前停止其他工具，重新授权 LocVela，再明确确认重试。异常退出未必执行 finally/onDestroy，待清理名称保留供恢复；卸载或清空数据前先处理恢复。

## iOS 开发后端

固定 pymobiledevice3 11.31.0 的 stopLocationSimulation 是 expects_reply=False。await clear 返回只表示调用/发送完成，状态为 CLEAR_SENT / sent_unconfirmed；不是设备确认，更不是恢复成功。

待恢复意图在第一次模拟前落盘；clear 发送、断连和退出都不会自动删除。断连且无法发送时进入 UNKNOWN。重新建立与同一设备的连接后显式 recover，只清理、不自动续跑。

用户在独立 Probe 观察新鲜位置并结合现实环境核对后，才能调用 verify_recovery；这只记录 user_confirmation_only，不是工具自动证明。Probe 仅前台读取，切回后建立新订阅；来源信息缺失不视作 false，非模拟标志也不是充分证据。

客户端租约到期、总时限、EOF、SIGINT/SIGTERM 和输出管道错误触发尽力清理。强杀、断电、拔线、被阻塞的主机 I/O 或上游取消不响应均可能妨碍及时处理，不承诺固定恢复时限。未收到确认时保留待恢复状态，不能只看程序退出。

## 共同约束

Rust 抽象状态机中需要清理回执的事件不能由 iOS send-only 返回伪造。现有 v1 兼容报告没有独立的 sent_unconfirmed/人工恢复证据字段，因此不得把它硬填为 cleanup=confirmed；报告协议升级并完成证据审核之前，不通过此路径生成 iOS passed 记录。

故障排查顺序：停止竞争工具 → 检查权限/配对/连接 → 明确重试清理 → 独立系统读取 → 检查微信具体功能。不得默认刷机、清空微信数据或修改用户 VPN。

导航、出行或紧急操作前，退出模拟并独立核对实际位置；工具不能保证固定秒数恢复。
